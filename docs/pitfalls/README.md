# Pitfalls Log

A living log of bugs, gotchas, and non-obvious behavior discovered during development.
Always check here before debugging something new — the answer may already be here.

---

## PITFALL-001: `react-router` vs `react-router-dom`

**Date discovered**: project start (Figma Make prototype)
**Symptom**: Import errors on navigation hooks
**Root cause**: The prototype uses `react-router` (v7), NOT `react-router-dom`. They are different packages with different export surfaces.
**Fix**: Use `import { ... } from 'react-router'`. In the Next.js migration, replace all of these with `next/navigation`.

## PITFALL-002: `motion/react` import path

**Date discovered**: project start (Figma Make prototype)
**Symptom**: `Module not found: motion` or wrong exports
**Root cause**: The animation library changed its import path. The package is `motion`, but the import is `motion/react`, not `framer-motion`.
**Fix**: `import { motion, AnimatePresence } from 'motion/react'`

## PITFALL-003: Dark mode uses `data-theme` attribute, NOT a CSS class

**Date discovered**: project start (Figma Make prototype)
**Symptom**: Dark mode styles don't apply; `[data-theme="dark"]` selectors have no effect
**Root cause**: `ThemeContext.tsx` (and the future Zustand store) sets dark mode via `document.documentElement.setAttribute('data-theme', 'dark')`, NOT `document.documentElement.classList.add('dark')`.
**Fix**: CSS selectors must use `[data-theme="dark"] .component { ... }`. Do NOT use `.dark .component` — that's Tailwind's default dark mode selector, which is not used here.

## PITFALL-004: `#main-scroll-container` is the scroll root, not `window`

**Date discovered**: project start (Figma Make prototype)
**Symptom**: `ReadingProgress`, `ScrollToTop`, and scroll-to-top-on-navigate don't fire; `window.scrollY` is always 0
**Root cause**: `Layout.tsx` sets `overflow-hidden` on the root div. The actual scrollable element has `id="main-scroll-container"`. All scroll events happen on that element, not on `window`.
**Fix**: Attach scroll listeners to `document.getElementById('main-scroll-container')`, not `window`. In Next.js, replicate this pattern in `app/layout.tsx`.

## PITFALL-006: Two color systems coexist intentionally

**Date discovered**: project start (Figma Make prototype)
**Symptom**: Hardcoded hex values (`#0347c1`, `#0458d4`, `#022a6e`) appear in components that otherwise use CSS variables — looks like a bug
**Root cause**: This is intentional. There are three color layers by design:
  - `--arm-*` CSS variables → light-mode surfaces (cards, glass panels, backgrounds)
  - `--arm-panel-*` CSS variables → dark panel interiors (RetroWindow `variant="dark"` content areas)
  - Hardcoded hex blues → structural chrome (Sidebar, Header, RetroWindow frame itself) that does NOT respond to dark mode
**Fix**: Do NOT replace the hardcoded hex values. They are structural. See DESIGN-SYSTEM.md.

## PITFALL-007: `next-env.d.ts` must not be committed

**Date discovered**: 2026-04-18 (Next.js migration)
**Symptom**: Git shows `next-env.d.ts` as modified after `next dev` or `next build`

## PITFALL-010: recharts `ResponsiveContainer` always warns `width(-1) height(-1)` on first render

**Date discovered**: 2026-04-19 (issue #6 — `/sobre` page)
**Symptom**: Browser console logs 4× "The width(-1) and height(-1) of chart should be greater than 0" on every page load, even with `next/dynamic({ ssr: false })`.
**Root cause**: `ResponsiveContainer` initialises with `containerWidth = -1, containerHeight = -1` as internal defaults. It fires the warning on the very first render frame, before its internal `ResizeObserver` has measured the DOM. This is a client-side timing issue — it happens regardless of SSR.
**What does NOT fix it**:
- `minWidth: 0` on the wrapper div — fixes a CSS flexbox shrink issue, not this
- `useSyncExternalStore(() => true)` — returns `true` immediately on the first client render; charts still render before measurement
- `useState(false) + useEffect setMounted` — correct in theory but blocked by the react-compiler lint rule ("avoid calling setState synchronously within an effect")
- `next/dynamic({ ssr: false })` alone — defers the JS bundle load, not the timing issue inside `ResponsiveContainer`
**Fix**: Remove `ResponsiveContainer` entirely. Use a `useWidth` hook that measures the container with a native `ResizeObserver`, then pass explicit `width={width} height={CHART_HEIGHT}` directly to the chart component. Guard with `{width > 0 && ...}` so the chart never renders with invalid dimensions. The `setWidth` call lives inside the `ResizeObserver` callback — not synchronously in the effect body — so the linter is satisfied.
**Location**: `components/content/SobreCharts.tsx`

## PITFALL-011: `unstable_doesProxyMatch` is in the docs but not in the package

**Date discovered**: 2026-09-26 (issue #76)
**Symptom**: `TypeError: unstable_doesProxyMatch is not a function` when testing the `proxy.ts` matcher, following `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`.
**Root cause**: on Next 16.3.6 (still true on 16.4.2) the docs shipped inside the package already use the new "proxy" name, but `next/experimental/testing/server` still exports the old one, `unstable_doesMiddlewareMatch`.
**Fix**: import `unstable_doesMiddlewareMatch`. When in doubt, the `.d.ts` files under `node_modules/next/dist/experimental/testing/server/` are the source of truth, not the docs.
**Location**: `lib/auth/route-guard.test.ts`

## PITFALL-012: Tailwind v4 `translate-*` and `scale-*` are not `transform`

**Date discovered**: 2026-09-26 (issue #92, plans 006 and 008)
**Symptom**: the mobile drawer (`Sidebar.tsx`) snapped open and shut with no animation, although its inline style declared `transition: "... transform 0.3s ease-in-out"`. Measured frame by frame: `-100%` to `0` in a single frame.
**Root cause**: in Tailwind v4, `translate-x-*`, `-translate-y-*`, `scale-*` and `rotate-*` set the individual CSS properties `translate`, `scale` and `rotate`, not `transform` (v3 used `transform`). A transition on `transform` never fires for them, and `getComputedStyle(el).transform` stays `none`. The prototype came from a v3 setup, so every inline `transition: transform` paired with one of these classes silently lost its animation in the port.
**Fix**: transition the property the class really sets (`translate`, `scale`, `rotate`), or use `transition-transform`, which in v4 covers all four. Read `getComputedStyle(el).translate` when measuring.
**Location**: `components/layout/Sidebar.tsx` (drawer), `components/content/PostsGrid.tsx` and `CommentsSection.tsx` (`hover:-translate-y-px`)

## PITFALL-013: `status: "HOLD"` does not hold a comment, the WordPress moderation option does

**Date discovered**: 2026-10-18 (issue #54)
**Symptom**: the code sends every comment with `status: "HOLD"`, yet a second comment from an email that already had an approved one went live with no moderation. Only a visitor's first comment waited in Pending.
**Root cause**: not our code. WordPress decides the status itself, and `createComment` does not override it. With "Comment must be manually approved" off (`comment_moderation = 0`), the only thing holding comments was "Comment author must have a previously approved comment" (`comment_previously_approved = 1`), which by definition lets returning commenters through. The result was identical with `HOLD` and with `APPROVE` (mutation test), which is what rules out our code.
**Fix**: set `comment_moderation = 1` on the production WordPress (Settings → Discussion → "Comment must be manually approved"), so every comment waits, returning commenters included. Done on 2026-10-18 and checked by `comments.live.test.ts`.
**Trap**: do NOT switch `comment_previously_approved` off to "fix" this. It is the opposite of what the label suggests: with moderation off, turning it off makes WordPress approve **everything** automatically. It happened once, a test comment went public for a few minutes, and it was reverted.
**Location**: `lib/graphql/mutations/comments.ts`, `lib/graphql/mutations/comments.live.test.ts`

## PITFALL-014: the comment mutation returns the held comment, so `comment === null` never means "queued"

**Date discovered**: 2026-10-18 (issue #54)
**Symptom**: after sending a comment, the screen did not show "✓ Comentário enviado! Aguardando aprovação." and listed the comment as if it were published (only for that visitor, and it vanished on reload). The unit tests were green.
**Root cause**: `/api/comments` decided `queued` by `!comment`, assuming WPGraphQL hides a held comment. But `createComment` runs with the admin application password, and an admin sees held comments, so the comment came back and `queued` was `false`. The unit test mocked `null`, a case the real WordPress never produced.
**Fix**: the mutation also asks for `status`, and the route answers `queued: true` (with `comment: null`) for anything that is not `APPROVE`. `route.test.ts` covers HOLD, SPAM and TRASH. `lib/auth/comments-route.live.test.ts` proves it against the real WordPress. A mock written from an assumption proves nothing about the real service: test the real one at least once.
**Location**: `app/api/comments/route.ts`, `lib/graphql/mutations/comments.ts`

## PITFALL-015: a parent category's count is `null`, and `revalidatePath` on a dynamic route needs `"page"`

**Date discovered**: 2026-10-18 (issue #73)
**Symptom**: (1) a category page showed 0 posts although its subcategories had posts. (2) `revalidatePath("/categoria/[category]")` throws in a route handler.
**Root cause**: (1) WordPress counts only the posts assigned directly to a category, and WPGraphQL returns `count: null` for one with none, even though a query filtered by the parent returns the children's posts. (2) With a dynamic segment, Next 16 requires the second argument: the pattern alone is ambiguous.
**Fix**: (1) `buildCategoryView` in `lib/categories.ts` sums the children and reads `null` as 0. (2) `revalidatePath(pattern, "page")`, as `app/api/revalidate/route.ts` does for both category routes; the docs in `node_modules/next/dist/docs/.../revalidatePath.md` are the reference.
**Location**: `lib/categories.ts`, `app/api/revalidate/route.ts`

## PITFALL-016: `next start` on localhost answers 500 on `/api/auth/*` with `UntrustedHost`

**Date discovered**: 2026-10-18 (issue #126)
**Symptom**: after `npm run build && npm start` (or the Vercel build run locally), `/api/auth/providers` and `/api/auth/session` return 500. The log says `[auth][error] UntrustedHost: Host must be trusted`. It looks like a regression from a dependency upgrade, but it is not.
**Root cause**: Auth.js trusts the host by itself on Vercel, and in `next dev`. In production mode anywhere else it refuses unknown hosts unless `AUTH_URL` or `AUTH_TRUST_HOST` is set.
**Fix**: for a local check only, start with `AUTH_TRUST_HOST=true`. Do not set it in `.env.local` or on Vercel: production already works without it, and the `AUTH_URL` of a real domain will be needed after the move to `blog.armandomonteiro.com` (see `docs/ECOSYSTEM.md`).
**Location**: `auth.ts`

## PITFALL-017: `editorBlocks` comes flat by default, code comes escaped, and the plugin is not on wordpress.org

**Date discovered**: 2026-10-18 (issue #84)
**Symptom**: (1) a list's items showed up as separate top-level blocks, and a quote's paragraph too. (2) a code block rendered `&lt;` as text, or `&amp;lt;` after one more escape. (3) `wp plugin install wpgraphql-content-blocks` finds nothing.
**Root cause**: (1) WPGraphQL Content Blocks returns every block in one flat list, each with a `parentClientId`, unless you pass `editorBlocks(flat: false)`. (2) the `content` attribute of `core/code` is already HTML-escaped. (3) the plugin is distributed only as a GitHub release.
**Fix**: (1) ask for `flat: false` and read `innerBlocks`, three levels deep. (2) `plainText()` decodes it once, and React escapes it as a child. (3) install the pinned zip from the release (see ADR-016); the introspection of the production schema is closed, so validate by running a real query, like `getPostBlocks` in `live.test.ts`.
**Location**: `lib/graphql/queries/posts.ts`, `components/content/single-post/PostBody/BlockRenderer.tsx`

## PITFALL-018: right after a plugin change, builds still show the old GraphQL error for up to an hour

**Date discovered**: 2026-10-18 (issue #84)
**Symptom**: the Content Blocks plugin was installed and active, `getPostBlocks` passed against production, yet `npm run build` kept logging `Unknown type "EditorBlock"` for the posts it had already fetched (all of them but the newest). The preview on Vercel showed plain text for a while too.
**Root cause**: a page with `revalidate = 3600` keeps the responses of its `fetch` calls in Next's data cache (`.next/cache/fetch-cache`, and the build cache Vercel restores) for that long. A GraphQL error comes back with HTTP 200, so the failed answer was cached like a good one.
**Fix**: nothing to fix in the code. After installing, removing or updating a WordPress plugin that changes the schema, wait up to an hour, or delete `.next/cache/fetch-cache` locally (`rm -rf .next/cache/fetch-cache`) before judging a build. The `revalidate` route (`/api/revalidate`) refreshes the page, not always the data cache entry, so do not rely on it for this.
**Location**: `.next/cache/fetch-cache`, `app/post/[slug]/page.tsx`

## PITFALL-019: locally, Vercel Analytics logs a MIME error that is not a bug, and the CSP needs no extra host for it

**Date discovered**: 2026-10-18 (issue #135)
**Symptom**: with `next start` on localhost and the security headers on, the browser console shows `Refused to execute script from '/_vercel/insights/script.js' because its MIME type ('text/plain') is not executable`. It looks like `X-Content-Type-Options: nosniff` broke Analytics.
**Root cause**: `@vercel/analytics` loads the script from the same origin, `/_vercel/insights/script.js`, a path that only exists on Vercel. Locally it is a 404 with `text/plain`. In production the same URL answers 200 with `application/javascript` (checked with `curl -sI`), so `nosniff` is harmless there. The `va.vercel-scripts.com` host only appears in the library's debug mode.
**Fix**: nothing to fix. Do not widen the CSP for it. `script-src 'self'` and `connect-src 'self'` cover Analytics in production; `va.vercel-scripts.com` and `vitals.vercel-insights.com` stay in the list only as a safety margin. To judge CSP violations locally, look only at messages that say "Content Security Policy".
**Location**: `next.config.ts`, `app/layout.tsx`

## PITFALL-020: `npm test` fails with dozens of unrelated errors when a copy of the repository lives inside the project folder

**Date discovered**: 2026-10-18
**Symptom**: `npm test` reported 48 failures in tests nobody touched (the output was full of `import * as Tests from "./data/match-path-data"`), right after several parallel agents had finished their work. Run again on a clean checkout, the same code had zero failures.
**Root cause**: the agents work in git worktrees under `.claude/worktrees/<name>/`, each with its own `node_modules`. Vitest's `exclude` only skipped the `node_modules` at the root, so it walked into the copies and ran the test files of the installed packages (and of the copied repository).
**Fix**: `vitest.config.mts` excludes `**/node_modules/**` and `.claude/**`. Also remove a worktree when its PR is merged (`git worktree remove <path>`; the branch stays). `.claude/` is not in `.gitignore`, so do not `git add .` there.
**Location**: `vitest.config.mts`

## PITFALL-021: validating an environment variable through a module does not replace reading it where it is used, for `NEXT_PUBLIC_*`

**Date discovered**: 2026-10-18 (issue #134)
**Symptom**: the obvious design for "validate the environment" is one module that parses `process.env` with a schema and exports the typed result, so every file reads from it. For a `NEXT_PUBLIC_*` variable that would leave the value `undefined` in the browser.
**Root cause**: Next inlines `process.env.NEXT_PUBLIC_X` into the client bundle at build time, and only when it is written as that exact literal. `process.env` itself does not exist in the browser, so a read through an object or a loop is not replaced. Components such as the header read the notification flag, so they must keep the literal read.
**Fix**: `lib/env.ts` only **checks** the variables, at build time and at start (called from `next.config.ts`, because `instrumentation.ts` does not run during `next build`). The reads stay where they are. `NEXT_PUBLIC_*` problems are warnings; a missing server variable fails the build, naming it and never printing a value. The production-only variables are required only when `VERCEL_ENV=production`, so CI and previews still build without them.
**Location**: `lib/env.ts`, `next.config.ts`
